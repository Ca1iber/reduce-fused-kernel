# v013：消除不必要的跨线程同步

v012设备代码显示tile512/threads128的copy dst与消费load均为stage_slot*512+threadIdx.x*4，每线程只消费自己拷贝的4个BF16。
因此对应ticket wait后不需要CTA barrier，slot重用也由同线程顺序保证。
保持相同tile/threads/stages，以owner_only开关做对照。
预测减少同步/控制指令及等待，减少与同步双buffer之间的差异。
生成代码地址映射若改变、出现跨线程读写、正确性不一致，方案不成立；不能把此条件外推到任意layout。



第二句话实际上只是一个待验证的假设，后来v013的实验没有支持它
当时的推理是：

### 1. 为什么认为可以省掉 CTA barrier

例如线程 0：

```
自己把数据拷到 shared[0:4]
自己从 shared[0:4] 读取并计算
```

线程 1 则只处理 `shared[4:8]`。

如果每个线程只读自己搬来的数据，并且 **ticket wait 已保证这些数据搬完、对该线程可见**，那么线程 0 就不用等待线程 1。因此推测可以省掉整个线程块的同步。

### 2. 为什么认为 slot 可以安全复用

同一个线程按照下面的顺序执行：

```
读完自己负责的旧数据
        ↓
把新数据搬到同一位置
```

如果这个先后关系得到保证，就不会覆盖自己尚未读取的数据，也不需要等其他线程。

### 3. 这个推理缺了什么

**地址对应相同，只证明“读写的是同一片位置”**它没有单独证明异步拷贝、shared 可见性、编译器排序和缓冲区复用都满足上述条件。

后来 v013 实测：

- 删除 CTA barrier：结果错误。
- 改成 warp 同步：结果也错误。

所以准确的表述应该是：

> 地址映射让我们怀疑 CTA barrier 可以省掉，但正确性实验否定了当前实现的这种修改。具体原因尚未定位，仍需保留 CTA barrier。
