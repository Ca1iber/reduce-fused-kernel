# reduce_fused Roofline 简报（sc-16g）

数据来自 2026-10-03 的聊天与实验记录，2026-10-04 重写。本次整理没有重新运行 GPU 测量。

## 1. 四个变体、四个 workload 在图上的关系

### 四个变体

共同计算：读取每个 token 对应的 K 个 expert 输出，用权重加权求和，写出一个 H 维结果；归约累加使用 FP32。

| 变体 | v001 颜色 | 缩放方式 | 输出 dtype |
|---|---|---|---|
| Base | 蓝色 | 只有路由权重 | 与输入相同 |
| XSF / WithXsf | 绿色 | 每行额外乘 `x_sf[pos]` | 与输入相同 |
| FP8 | 橙色 | 归约结果额外乘全局 `sf[0]` | FP8 e4m3fn |
| Quantized | 粉色 | 同时使用 `x_sf` 和 `sf` | FP8 e4m3fn |

FP8 / Quantized 的输入仍是本次的 FP16/BF16，名称主要反映缩放和 FP8 输出，并非所有计算都采用 FP8 算术。

### 四个 workload

| Workload | T：token 数 | K：top-k | H：hidden | 输入 dtype | v001 形状 |
|---|---:|---:|---:|---|---|
| tiny | 32 | 2 | 256 | FP16 | 圆点 |
| h3072 | 512 | 8 | 3072 | BF16 | 方形 |
| h7168 / decode | 512 | 8 | 7168 | BF16 | 菱形 |
| prefill | 4096 | 8 | 7168 | BF16 | 三角形 |

### 为什么会分成这些组

1. **Base 与 XSF 挨在一起。**它们的主要读写量相同；`x_sf` 只增加少量缩放数据和计算，摊到较长的 H 上，影响较小。实测延迟和有效带宽也接近。
2. **FP8 与 Quantized 挨在一起。**它们共享全局缩放和 FP8 输出路径，增加 `x_sf` 对总耗时的影响较小。
3. **橙色、粉色相对更靠右。**FP8 输出每个元素只写 1 字节，而 Base/XSF 写 2 字节，同时增加输出缩放的逻辑 FLOPs。因此 FLOPs/Byte 更高；右移不表示更快。
4. **Base/XSF 更靠近斜线。**大 workload 的有效带宽较高；FP8/Quantized 虽然输出更小，耗时却更长。现有变体将 `sf` 与 FP8 转换绑在一起，不能把延迟差全部归因于缩放乘法，转换/指令路径仍需要分析。
5. **tiny 在底部。**工作量很少，无法像大规模流式访问一样摊薄固定执行成本。低吞吐不能直接解释成存在百倍可实现加速。
6. **h7168 与 prefill 的图接近。**两者 H、K、dtype 相同，prefill 的 T 是八倍，FLOPs 与字节数也大致同增八倍，所以算术强度几乎不变。Base/XSF 的带宽也接近，点会接近，但绝对耗时相差约八倍。

逻辑算术强度 `AI = FLOPs / 字节数`：Base/XSF 的大 workload 约 **0.889 FLOP/Byte**，FP8/Quantized 约 **1.0 FLOP/Byte**。相比 v001 经验计算/带宽交点约 **14.94 FLOP/Byte**，都位于模型的带宽侧；但这不证明实际 HBM 已经跑满。

以上颜色、形状对应 [v001 的 16 点汇总图](../../v001_DIS:v000/analysis/roofline.html)。v002 是单 case 的 mcProfiler 图，颜色区分 HBM、L2C、VL1 等层级，不能沿用 v001 的颜色含义。原计划采 12 张，后来按上述 h7168/prefill 相似的观察缩减为 9 张：Base 三种规模，其他变体各两种。

## 2. 理论带宽、实测带宽与“上限”

### mcProfiler 的理论参考：1.8432 TB/s

当时 mcProfiler 3.8.1.4 的内部 Roofline 模型使用：

```text
max_DnocRWPerCycle = 2048 字节/周期
mc_clk = min(core_clk, 0.9 GHz)
2048 × 0.9 = 1843.2 GB/s = 1.8432 TB/s
```

这是工具的总读写带宽模型常量与时钟参数，不是当前 sc-16g 实测出的持续上限。也不能因为 `Compute 25%` 就直接将 HBM 带宽除以四。

原生图的横纵坐标经过归一化，不能直接当作未经缩放的 AI、TFLOP/s；同时缩放两轴不改变点与 HBM 斜线的相对比例，因此工具给出的 HBM Usage 仍保留其模型含义。

### 几次实测说明了什么

| 测试 | 计时口径 | 最高/代表结果 |
|---|---|---:|
| v001 PyTorch copy/add 校准 | GPU 时间线 | **1.4823 TB/s** |
| 独立原生 Copy/Triad | GPU events | Copy 最高 **1.4412 TB/s** |
| 原生 8:1 读写探针 | GPU events | 最高 **1.4294 TB/s** |
| 后来统一计时的 Copy | GPU 时间线 | 最高 **1.4508 TB/s** |
| 后来统一计时的 8:1 探针 | GPU 时间线 | 最高 **1.4713 TB/s** |
| 后来统一计时的 Base/XSF | GPU 时间线 | 大 workload 约 **1.48～1.49 TB/s** |

**测速程序达到的带宽，不等于硬件最多只能达到的带宽。**Copy 是 1:1 读写，Triad 是 2:1；Base/XSF 的主体流量约 8:1。即使比例一致，FP32/float4 探针与 BF16 gather kernel 的布局、线程安排也不同。

因此，之前“1.44 TB/s 就是容器上限”的判断已经撤回。**1.49 TB/s 可以作为当前实验的经验参考，但还不是证明过的硬上限。**“接近上限”的表述需要限定 workload、流量和参考值。

### 为什么 mcProfiler 的 84% 会算出约 1.55 TB/s

以 Base h7168 为例：

| 来源 | 字节数 | 耗时 | 带宽 |
|---|---:|---:|---:|
| mcProfiler 计数/周期换算 | 66.107 MB | 42.673 μs | **1.5492 TB/s** |
| 原 benchmark GPU 时间线 | 66.093 MB | 44.436 μs | **1.4874 TB/s** |
| 后来统一 GPU 时间线计时 | 66.093 MB | 44.288 μs | **1.4923 TB/s** |

mcProfiler 使用 `48,007 / 1.125 GHz` 换算时间，并以 `1.5492 / 1.8432` 得到 **84.05%**。流量几乎相同，约 4% 的计时差造成了带宽差。

**同口径复测没有确认稳定的 1.55 TB/s。**时钟换算、采集方式和运行波动各自影响多少仍未确定，不能据此断言 profiler 错了，也不能把 1.55 写成已确认上限。图内 events 未正确更新时间的那次尝试已被丢弃，不纳入这些数据。

## 3. 数据与当前判断

### 原始 16 组 naive 耗时

单位：**μs**。来源：[benchmark.csv](../../v001_DIS:v000/raw/benchmark.csv)。原协议为 10 次 warmup、50 次 repeat × 3 trials、每轮清理 L2，使用 GPU 时间线计时。

| Workload | Base | XSF | FP8 | Quantized |
|---|---:|---:|---:|---:|
| tiny | 3.702 | 3.712 | 4.844 | 4.833 |
| h3072 | 21.263 | 21.386 | 42.040 | 42.138 |
| h7168 | 44.436 | 44.549 | 94.408 | 93.926 |
| prefill | 357.422 | 358.856 | 427.914 | 431.631 |

### 以 1.49 TB/s 为假定参考的有效带宽利用率

计算方式：`语义读写字节数 / kernel 耗时 / 1.49 TB/s`。

| Workload | Base | XSF | FP8 | Quantized |
|---|---:|---:|---:|---:|
| tiny | 0.90% | 0.90% | 0.57% | 0.58% |
| h3072 | **89.46%** | **89.00%** | 42.74% | 42.67% |
| h7168 | **99.82%** | **99.60%** | 44.38% | 44.62% |
| prefill | **99.28%** | **98.91%** | 78.32% | 77.67% |

这是按模型字节数算出的**有效带宽利用率**，不是硬件计数器直接测得的 HBM 利用率。模型包含输入、输出、权重、索引、缩放因子；当前输入生成可能重复一行，对大 workload 流量估算影响不到 0.03%。

### 统一计时复测的 Base / XSF

协议：10 warmup、31 个 kernel 时间取中位数，每次调用前用 64 MiB 缓冲清理缓存，清理时间排除。完整探针对比见 [unified_bandwidth_16g.csv](../raw/unified_bandwidth_16g.csv)。

| Workload | 变体 | 耗时 μs | 有效 TB/s |
|---|---|---:|---:|
| h7168 | Base | 44.288 | 1.4923 |
| h7168 | XSF | 44.544 | 1.4841 |
| prefill | Base | 356.608 | 1.4827 |
| prefill | XSF | 357.888 | 1.4778 |

与原 benchmark 的差异不到 0.34%，没有改 GPU 代码，因此不作为优化收益。最新 Base h7168 相对 1.49 约 100.16%，也说明参考值只是近似。

### 判断

- **Base/XSF 的 h7168、prefill：**接近当前实测带宽水平。在搬运量不变、1.49 参考可达到的条件下，继续提高带宽的空间很小；不能写成绝对没有优化空间。
- **Base/XSF 的 h3072：**约达到参考值的 89%，纯带宽模型仍有约 **10%～11% 的耗时下降空间**。
- **FP8/Quantized：**h3072、h7168 的有效带宽约 43%～45%，优先检查 FP8 转换和指令路径；目前尚未确定具体限制。
- **tiny：**纯带宽模型不适合估算其优化空间，暂不优先；若实际调用频繁或评分等权，再提高优先级。

即使 HBM 利用率接近满载，也要确认搬运量接近最少；多搬冗余数据的实现同样可能跑满带宽。判断是否接近极限，应同时比较 `必要字节数 / 可达到带宽` 与实际耗时。

九组 mcProfiler 原始计数见 [recovered_roofline_counters.json](../raw/recovered_roofline_counters.json)。其余原始 PNG 和遗失手写报告尚未全部找回；本报告重建的是聊天中的数据和讨论结论。
